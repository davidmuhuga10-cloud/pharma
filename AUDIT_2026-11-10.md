# Pharma — security, reliability and readiness audit

**Date:** 10 November 2026
**Scope:** the PHARMA Supabase project (`ovegzdlrhlcpjfcsoumu`), the web app in
this repository, the Netlify functions and the Edge Functions.
**Not touched:** the separate Hotel Management project, as instructed.

Everything below was checked rather than assumed. Where something is reported
as working, this says how that was established. Where a check was inconclusive,
it says so.

---

## The short version

Four real defects were found and fixed. Two were authorization holes that an
ordinary signed-in employee could have used; one was a broken button that is
almost certainly affecting users today; one was a missing backup that would
have meant losing the business if the project had been lost.

The parts of the system that matter most — the money and stock arithmetic, the
tenant isolation, the indexing — were examined closely and are **sound**. The
database is in better shape than most systems of this age.

**Readiness to take on the first few pharmacies: yes**, with two caveats listed
at the end that are business decisions rather than engineering ones.

---

## 1. What was wrong, and what was done

### 1.1 A deactivated account could still call 42 functions — FIXED

**The defect.** 42 database functions guarded access with

```sql
if p_pharmacy_id is distinct from my_pharmacy_id() then
  raise exception 'Not authorized for this pharmacy';
end if;
```

`IS DISTINCT FROM` is NULL-safe: it treats two NULLs as equal. And
`my_pharmacy_id()` deliberately returns NULL for an account that has been
switched off, has expired, or whose pharmacy's plan has lapsed. So a caller in
exactly that state, passing `p_pharmacy_id` as NULL on purpose, had
`NULL IS DISTINCT FROM NULL` evaluate false — **the guard did not fire**.

**How bad.** For 38 of the 42, the call then failed later on an unrelated check,
so nothing leaked. But four did their work and returned:
`cash_drawer_summary` and `dashboard_data_custom` (another pharmacy's money
figures), `quote_sale` (priced a sale), and `set_sms_enabled` (toggled SMS) —
all for an account with no valid session.

**The fix.** One line per function, adding an explicit NULL test ahead of the
comparison. Nothing else changed.
`migrations/2026-11-10_close_null_pharmacy_guard.sql`, with its rollback.

**How it was verified.** On a throwaway Postgres loaded from an unmodified
`schema.sql`, every one of the 42 functions was called as a deactivated user
and as an expired user, passing NULL. Before: 4 returned successfully, 38 failed
late. After: **42 of 42 refuse immediately.** The pre-existing cross-tenant
cases (an attendant of one pharmacy aiming at another, a fired employee aiming
at their old one) produced byte-for-byte identical results before and after, so
nothing that already worked was disturbed. Confirmed again on the live project
after applying.

### 1.2 A hidden button could be bypassed by calling the API directly — FIXED

**The defect.** Four screens wrote their table directly over the REST API
instead of going through a role-checked function, and those tables' row-level
security policies only check the *pharmacy*, not the *role*. So the role gate
existed **only in the browser** — while `js/core.js` lines 25-27 state the
opposite:

> "This only decides what the screen offers. The real gate is the database …
> so a hidden button can never be bypassed by calling the API directly."

Measured against the live database, every role could do all of these:

| Write | Why it matters |
|---|---|
| `drugs` UPDATE | **No screen uses it at all.** It let anyone switch off `is_prescription` — the exact flag `record_sale` reads to decide whether a patient must be recorded — so a prescription-only medicine could be sold with no patient recorded. Also hiding a drug, or changing its price. |
| `batches.discount_percent` | `record_sale` and `quote_sale` price a line as `sell_price × (1 − discount_percent/100)`. Writing 100 sells that batch **for nothing**. |
| `suppliers` INSERT | Includes `opening_balance`, which feeds what the pharmacy believes it owes. |
| `insurance_claims.status` | A claim could be marked paid by anyone. |

`control_class` was already safe, via the existing
`trg_protect_drug_control_class`.

**The fix.** `drugs` UPDATE was revoked outright — nothing anywhere uses it
(checked every file in `js/`, `admin.js`, `install.js`, the Netlify functions
and the Edge Functions). The other three keep working **with no change to any
screen** and gained a `BEFORE` trigger enforcing the same rule the screen
shows, following the pattern already used by `protect_pharmacy_billing`,
`protect_sms_cap` and `protect_drug_control_class`.
`migrations/2026-11-10_role_checks_on_direct_writes.sql`, plus
`..._role_check_triggers_invoker.sql` which corrects the first one (see §3).

**How it was verified.** All five roles against all five writes, before and
after, on a local copy. Before: everything allowed for everyone. After: a
seller refused on all five; an accountant only claim status (correct —
`claims` is in `ACCOUNTANT_ACTIONS`); a stock taker only adding a drug; owner
and pharmacist unaffected. `import_stock_rows`, `sync_master_drugs`,
`record_restock` and `record_sale` all still work. On the **live** project,
signed in as the real seller account, all guarded writes were refused and the
owner's still worked — each attempt inside a rolled-back transaction, with
"nothing left behind" confirmed afterwards.

The drug-insert gate deliberately also allows a stock taker, wider than the
Add-a-drug screen's `can('edit_inventory')`, because `import_stock_rows` and
`sync_master_drugs` create drugs and already allow that role. A narrower rule
would have broken Import and "Sync common drugs".

### 1.3 A drug with an apostrophe in its name broke its buttons — FIXED

**The defect.** Buttons were built as
`onclick="openWriteOff('<id>','<drug name>',<qty>)"` with the name passed
through `esc(name).replace(/'/g, "\\'")`. That guard **does nothing**: `esc()`
has already turned every `'` into `&#39;`, so the `.replace()` finds no quotes.
The browser then HTML-decodes the attribute *before* parsing the JavaScript,
turning `&#39;` back into a real quote, ending the string early and leaving
invalid JavaScript.

**How bad.** Any drug named "Jack's Cough Syrup" or "Children's Panadol" — and
apostrophes are common in medicine names — had **Write off, Return to supplier,
Correct count, Mark down, Edit expiry, Edit price and Return all silently do
nothing.** No error, no message, just a dead button. This is very likely
affecting real users today. The same mechanism meant the escaping was not
actually containing the value, which is a security concern as well.

**The fix.** A new `jsArg()` beside `esc()` in `js/core.js`, used at the 7
affected call sites (6 in `js/stock-actions.js`, 1 in `js/reports.js`). It
escapes for the one position `esc()` cannot cover, turning anything dangerous
into a `\uXXXX` escape, which survives HTML decoding unchanged. `esc()` is
untouched and remains correct for HTML.

**How it was verified.** The real `esc()` and `jsArg()` were lifted out of the
shipped `js/core.js` and run against names with apostrophes, double quotes,
ampersands, angle brackets and newlines, simulating the browser's
decode-then-parse. Before: `SyntaxError` — a dead button. After: **7 of 7**
parse and the handler receives the name exactly as typed. `esc()` re-checked
separately and unchanged.

### 1.4 There was no backup you could restore from — FIXED

Supabase Free keeps none. The business — 532 sales, 3,246 sale lines, 389
drugs, 299 batches, 14 customers, 4 pharmacies — had no recoverable copy.

There is now an automatic, **restore-tested** nightly backup in a separate
**private** repository, `davidmuhuga10-cloud/BACKUPS`, at 04:17 Nairobi time.
It costs nothing. Full detail, including how to restore, is in `OPERATIONS.md`
under "Backups and recovery".

It had to be a different repository because `davidmuhuga10-cloud/pharma` is
**public**, and the dumps contain patients' names and phone numbers,
controlled-drug records, customers' debts and the password hashes in
`auth.users`. (While setting it up the public repo was scanned: no secrets are
leaking — `config.js` holds only the publishable key, which is public by
design.)

**Two bugs that testing caught, which would have made the backups worthless:**

- The first version judged success by counting tables. Run against an empty
  database it reported **zero errors and zero rows** — it would have committed
  an empty dump every night for ever, showing green. Comparing against row
  counts taken from the live database first is the only check that catches that.
- **Restore order.** `public.profiles.id` references `auth.users(id)`, so
  restoring `public` first leaves Postgres unable to re-create
  `profiles_id_fkey`; it drops the constraint with only a warning. `auth.users`
  must go first. The nightly run now asserts that key exists afterwards.

**Verified** locally (43 tables at exact row parity, rotation tested over 18
simulated days keeping exactly 14) and then for real: run #2 succeeded in
1m 34s, having verified 43 tables and 9,162 rows restore exactly.

## 2. What was examined and found sound

These were checked carefully and needed no change. Listing them matters as
much as the fixes — it says where the system has been looked at.

**Money and stock arithmetic.** On the live data: sale totals reconcile with
their line items and payments; **all 299 batches reconcile exactly** against
the full adjustment ledger (`quantity_remaining = quantity_received + sum of
adjustments`); no duplicate invoice numbers; no orphaned rows; no negative or
zero payments. This is the part a pharmacy cannot afford to have wrong, and it
is right.

> A note on method: an early version of that reconciliation query used the
> wrong column and flagged 299 of 300 batches as broken. That was a bug in the
> check, not the data. The corrected query returns zero bad rows. Mentioned
> because the first number was alarming and wrong.

**Tenant isolation.** No cross-tenant foreign-key references anywhere. Every
RLS policy on the business tables scopes by `pharmacy_id = my_pharmacy_id()`,
and because `WITH CHECK` is omitted Postgres reuses the `USING` expression, so
rows cannot be written into another pharmacy either.

**The admin surface.** All 12 `admin_*` functions — including
`admin_delete_pharmacy` — guard with `is_platform_admin()` as their **first**
statement, and that function is correct (`exists (select 1 from platform_admins
where user_id = auth.uid())`, which fails closed for an anonymous caller). Not
taken on trust: all 12 were called as the real attendant account with harmless
arguments in rolled-back transactions. **All 12 refused.**

**Indexing.** Every foreign key has a supporting index — **zero unindexed
foreign keys**, which is unusual and good. Every busy table has a
`pharmacy_id`-leading index and they are heavily used
(`sale_items_pharmacy_id_drug_id_idx` 5,095 scans,
`drugs_pharmacy_id_active_idx` 3,932, `sales_pharmacy_created_idx` 2,408).
`batches_fefo_idx` is a textbook partial covering index matching the FEFO drain
exactly.

**The 30 "unused index" advisor warnings: do not act on them.** Every one sits
on a tiny table — `expenses` 29 rows, `suppliers` 1, `controlled_ledger` 0, the
largest 60. Postgres will never use an index on a 29-row table because scanning
29 rows is cheaper. `idx_scan = 0` here measures your *data volume*, not the
index's worth, and the names are exactly the tenant-scoped and foreign-key
indexes you need at 50 pharmacies. They cost **344 kB on a 7 MB database**.
Dropping them would mean deleting the scale preparation precisely because you
have not scaled yet.

**The 9 "RLS enabled, no policy" advisor warnings: correct as they are.** All
nine (`platform_admins`, `phone_otps`, `sign_in_log`, `support_session` and
friends) grant **no privileges at all** to `authenticated` or `anon`. RLS on,
no policy, no grants is fully locked down — these are service-role-only tables.

**Edge Functions and payments.** All six Edge Functions and the Netlify/M-Pesa
functions were read in full. No issues found. The OTP rate-limiting,
constant-time secret comparison and the idempotent crediting in the M-Pesa
callback are genuinely well built.

**Performance.** `dashboard_data_raw` for a month returns in **21.6 ms**. The
SMS queue is clean — nothing stuck, nothing unrefunded. `fetchAllRows()`
correctly pages around PostgREST's 1,000-row limit, which is a real trap that
was already handled.

**Code quality.** Across ~9,800 lines of frontend JavaScript: **zero
`console.log` or `debugger`** left in, **zero TODO/FIXME markers**, and only 5
awaited database calls without visible error handling — all of which turned out
to be safely written anyway (`sups || []` and similar).

**The test suite.** 38 test files. Run with the fixes applied: **32 of 32 pass**
in the main suite, plus `native-shell`, plus 18 assertions in `send-sms`. Zero
failures. `android-shell` could not be run from the audit environment because
`MainActivity.java` sits deeper than the file-staging limit allows; its one
assertion that touches a file changed here (`sw.js` must list
`./nativeShell.js`) was verified by hand. **Run `npm test` locally once to
close that last one.**

## 3. A mistake made during this work, and how it was caught

The four trigger functions added in §1.2 were first created `SECURITY DEFINER`
with default grants. That put them on the REST surface as
`/rest/v1/rpc/protect_*` and raised a **new** Supabase advisor warning. Nothing
was exploitable — Postgres refuses a trigger function called outside a trigger
— but it broke the project's own `MIGRATIONS.md` rule 6 and left a warning on
the dashboard.

It was caught by checking the advisors after applying, which the project's own
release checklist requires. Corrected by
`migrations/2026-11-10_role_check_triggers_invoker.sql`: `SECURITY INVOKER`
(matching the three trigger functions the project already had, which is why
those never appeared in the advisor) with execute revoked. A trigger does not
need EXECUTE on its function to fire. Behaviour re-verified identical
afterwards, on both the local copy and live.

Recorded here because the checklist step is what caught it, and that step earns
its place.

## 4. Open items — these need you, not code

1. **Supabase Free plan.** The missing-backup half is now solved. What Free
   still costs: the project **pauses after about a week of no activity**, and
   there is no point-in-time recovery, so the most that can ever be lost is one
   day. With paying pharmacies, moving to Pro is the right call — but it is no
   longer what stands between you and losing the data.
2. **Leaked-password protection** is off (Auth → Attack Protection). May need a
   paid plan.
3. **The paying pharmacy is recorded as `trial`, expiring 2027-12-31.** Mark it
   paid in the admin console so billing reports are right.
4. **Run `npm test` once locally** to close the one test this audit could not
   run.
5. **The rush-hour chart was built and never wired up.** `dashboard_data_raw`
   computes a `rush` figure on every dashboard load and nothing displays it —
   `dashRushGraphHtml()` in `js/dashboard.js` is never called. Either wire it
   up or drop both. Not urgent: the whole dashboard is 21.6 ms. (Profit is
   *not* in this category — `dashProfitHtml()` is dead, but profit itself is
   displayed by other live code.)
6. **Six unused functions**, ~67 lines total: `controlledLevel()` (core.js:77),
   `balanceBadge()` (customers.js:183), `dashRushGraphHtml()` (dashboard.js:525),
   `dashProfitHtml()` (dashboard.js:630), `parseFlexibleExpiry()` (import.js:82),
   `valuationLine()` (reports-stock.js:233).

   **Deliberately not deleted.** Several are feature-shaped — `parseFlexibleExpiry`
   parses "12.2027" month-year expiries, which is how Kenyan supplier sheets
   often write them, and may be a feature that was half-wired rather than
   abandoned. Deleting someone's intended work days before going to market is
   a bad trade for a cosmetic gain. They are listed so the decision is yours.

7. **Cosmetic.** About 37 functions say "Only the owner…" while also allowing
   co-owner; two spell out "or co-owner". The first is clearly the house
   convention, so the two outliers are the inconsistency. Not worth churning 39
   messages.

## 5. Taking it to market

**The engineering is ready for the first several pharmacies.** The money and
stock arithmetic is correct and was checked against real data; tenancy holds
under direct API attack, not just in the UI; the admin surface is properly
gated; the indexing is built for more load than you have; there is now a backup
that is proven restorable every single night.

Two things to be clear-eyed about, both business decisions:

- **The Free plan pauses after ~a week of inactivity.** With real pharmacies
  using it daily this will not trigger — but a pharmacy that signs up and goes
  quiet for a fortnight will find the app down. That alone is reason enough to
  move to Pro once money is coming in.
- **The backup window is 24 hours.** Losing a day's sales is survivable;
  losing everything is not, and that is now covered. Closing the 24-hour gap
  needs paid point-in-time recovery, not a more frequent dump.

Neither blocks you from going out and signing the first five.
